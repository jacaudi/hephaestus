Example: boot SystemRescue once on the machine with MAC 52:54:00:e2:e0:03. Highlighted = new in M2. The UI (M4) later calls the same code path.

Next boot of that machine

  1. iPXE → /boot (TLS)
  2. ↓ decision row 3: boot-next set and ready?
  3. ready → SystemRescue script, second stage over plain HTTP from the store; boot_next cleared
  4. not ready → flag kept, rows 4–10 apply as today, fetch queued

Only the serve process writes the content store. The store index is not safe for two writers.

A · recommended

CLI inside the container writes the database

  1. You, on the TrueNAS host: docker exec hephaestus /hephaestus boot-next 52:54:00:e2:e0:03 systemrescue
  2. ↓ same binary, same config, same repository code
  3. DB: boot_next = systemrescue; utility_cache.systemrescue = wanted
  4. ↓ serve's fetcher polls wanted rows every 10 s
  5. serve fetches, checks the pinned sha256, extracts, sets ready
  • No new network surface: access to the host is the authentication
  • Works with SQLite (WAL, busy timeout) and Postgres
  • Also: boot-next clear, utility fetch <entry>, utility list
  • Needs a shell on the host (fine for one owner)
  • Fetch starts within 10 s, not instantly
B

Admin-listener HTTP endpoint, CLI is a thin client

  1. You, anywhere on the management LAN: hephaestus boot-next … --admin 10.0.10.5:9090
  2. ↓ POST /admin/boot-next
  3. serve writes the DB and starts the fetch immediately
  • Instant fetch; works from a laptop without host access
  • The admin listener has no authentication until M4 (§5.8). Anyone on the management LAN could boot-next ShredOS (a disk wipe) onto any machine.
  • So it needs a stopgap token now that M4 then replaces
  • Turns a read-only listener (health, metrics) into a control plane

Dropped: a config file listing boot-next targets. A one-shot flag that a static file re-arms on every restart is the wrong shape.
