Alpine aarch64 (D18): where its offline tools come from

The netboot tarball (kernel, initramfs, modloop) is pinned by hash like every other entry. The open question is only the apk packages (nwipe, memtester, partclone, ddrescue, testdisk, zfs-lts and the alpine-base that Alpine's init always installs).

  • Alpine keeps one version per package and rewrites APKINDEX.tar.gz in place (last change 2026-11-16 02:37 GMT). A pinned .apk URL returns 404 once superseded, so pinning hashes against the live repo breaks within days.
  • Netboot 3.24.4 runs kernel 6.18.60-0-lts; the repo's zfs-lts is built for 6.18.63. ZFS only works when the two match.
  • Tools live in two repos: main (testdisk, zfs-lts) and community (nwipe, memtester, partclone, ddrescue).
A · recommended

Snapshot at first fetch, trust Alpine's signing keys

  1. First utility fetch alpine (in serve)
  2. ↓
  3. download today's APKINDEX for main + community; verify its signature against Alpine's apk keys pinned in the binary
  4. ↓
  5. resolve the closure, download each .apk, check each against the signed index's checksum
  6. ↓
  7. store the snapshot; serve it as alpine_repo=http://10.10.20.5/u/alpine/3.24.4/apk/main,…/community
  • Offline after the first fetch, no publishing anywhere
  • The same trust model Alpine itself uses
  • zfs-lts is added only when its kernel matches; utility list says "ZFS unavailable" otherwise
  • apk bytes are checked against Alpine's signing key pinned in the binary, not a per-file hash pinned in the binary: one stated exception to the anti-goal
  • Two installs fetched on different days can hold different apk versions

Trust anchor: Alpine's apk signing keys, committed with provenance.

B

Publish a pinned snapshot to a URL you own

  1. task catalog:pin on your Mac
  2. ↓
  3. builds the snapshot (index + apks), uploads it as one tarball to e.g. a release in your Forgejo/GitHub repo
  4. ↓
  5. its sha256 is pinned in the binary; hephaestus fetches it like any other container
  • Every byte checked against a hash pinned in the binary, with no exception
  • Every install gets identical packages
  • Needs a remote, and publishing on every re-pin (outward-facing, needs your approval each time)
  • About 300 MB per snapshot to host; you redistribute GPL packages (source offer applies)

Trust anchor: a hash pinned in the binary.

C

Alpine tools stay online

  1. Cache only the netboot tarball
  2. ↓
  3. alpine_repo=https://dl-cdn.alpinelinux.org/… at boot; Alpine's init verifies apks itself
  • Smallest build; no snapshot logic
  • The booted machine needs internet, and the provisioning VLAN may have none
  • Breaks "offline after first fetch" (core goal 4) for the one arm64 rescue OS

Trust anchor: Alpine's keys, checked by the booted machine.
