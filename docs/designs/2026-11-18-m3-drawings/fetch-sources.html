M3: How Talos Downloads Join The Fetcher

The handoff's constraint: Talos prefetch reuses the existing pool, so there is no second fetcher. Today the pool (internal/toolcache/fetcher.go) claims only utility_cache rows, looks each up in the compiled-in catalog, downloads whole objects, checks pinned hashes, extracts files and tags them. A Talos download differs in four ways: its URL is built from (schematic, version, arch); it goes through a one-hour signed redirect; nothing is pinned, so the sha256 is recorded at the first fetch; and nothing is extracted. M3b then adds a third kind, installer images, which are registry pulls rather than file downloads. Highlighted = new.

Shared By Both Options

  • One pool of HEPHAESTUS_FETCH_WORKERS (default 4), one space-reservation ledger (2× the object size, 1 GiB margin counted once), one 32 KiB/s floor, resume with Range + If-Range, and every blob fsynced in store.PushBlob (your choice A).
  • Claim order (my call): armed boot-next utilities first (priority 1, as today), then Talos assets for assigned machines, then everything else, oldest first.
  • store.ContentLost stays the only lost-content test; startup reconciliation recomputes assets_ready from the store.

One Pool, One Job Per Source

  1. A worker asks the sources in claim order: utility source, then Talos source
  2. ↓ the source that has a row returns a job
  3. Each source owns its job: the utility job is today's code moved behind the seam; the Talos job builds the factory URL, follows the redirect, records the sha256, tags
  4. ↓ both call the pool's shared helpers
  5. download with resume and the floor, reserve space, push, tag

  • Patchbay: a new kind is a new source, never an edit to its siblings

One Table, A Kind Column

  1. utility_cache gains kind (utility | talos) and the key widens to hold a schematic and version
  2. ↓ one claim query, as today
  3. The job branches on kind at each step: catalog lookup or factory URL, pinned or recorded hash, extract or not
4branch points in the job; M3b adds a third kind to each
  • One claim query and one table to reconcile
  • A growing switch every new kind edits, the wall Patchbay warns about
  • A widened key and nullable columns weaken the utility table's constraints
  • An installer pull (manifests and blobs) fits none of the four branches

Not offered: a second fetcher for Talos. The handoff rules it out, and it would split the worker count and the space ledger.
