M3: design it as one milestone, or split it?

Scope comes from the core design's Milestones list. Each milestone gets its own design, plan, plan gate and unattended run, and is merged locally into main. Highlighted boxes show what works the day each piece merges. Task counts are my estimates from that scope, not plan output.

The Same In Every Option

  • There is no UI until M4, so approve, adopt and cluster import are CLI commands run inside the container, the way M2's boot-next works. The CLI calls the same fleet functions the M4 UI will.
  • Talos downloads go through the existing fetcher pool (4 workers, the 32 KiB/s floor, the space reservations) into the same content store, and store.ContentLost decides when content is lost.
  • Host binding keeps the MAC-bound boot-next rule (flagServesMAC). A junk-UUID machine never gets an install.
  • Native clusters (the create form, the YAML editor with a diff, the 1Password writer, export) are built around forms that arrive with the M4 UI. Where they land is the next question, so they are left out of the counts below.

M3b · Offline Installs

~8tasks (est.)
  • Installer index prefetch, every arch in use
  • /v2/ mirror: allow-list, routing contract, 404 on a miss with a background fetch
  • Talos pins and the runtime GC quiet window
Installs succeed with egress blocked (success criterion 1 in full).
  • Each piece is no bigger than M1, the largest run that has finished
  • The first piece ends in a real install, so nothing ships idle
  • The mirror and GC are built against Talos content that already works
  • Until M3b, installs need internet for the installer pull
  • Talos content is not garbage-collected until M3b; one tuple's kernel and initramfs are roughly 100 MB (my estimate, not measured)
