Talos Assets: What Survives A Power Cut?

Example: talos-04-wrk is approved. hephaestus has just fetched its kernel-amd64 (21,627,392 bytes) and initramfs-amd64.xz (78,894,177 bytes, both measured on factory.talos.dev for v1.12.11 today), tagged them, and set assets_ready. Seconds later the lab loses power.

Corrected after the design gate (2026-11-18). index.json is fsynced and written atomically (SyncIndex: true, internal/store/store.go:116; oras-go v3.0.0 content/oci/atomicwrite.go). But neither layer blobs nor the manifest are fsynced: TagArtifact pushes the manifest through oras.PackManifest → oci.Push, which indexes and saves it without syncing its bytes. So the synced index can name a short or zeroed manifest, and on reopen the verified index load fails and the whole store is set aside (docs/utility-content.md:29). M2's original note was right; my first version of this box said otherwise and was wrong. Option A therefore covers the manifest and its empty config blob as well as the layers.

After Power Returns, Without A Fix

  1. The tag is on disk (the index was fsynced) and names the kernel blob
  2. ↓ but the blob's data may never have reached the disk
  3. Case 1: the blob is short or empty → the startup layer check finds the wrong size → store.ContentLost → assets_ready cleared, refetch queued. talos-04-wrk holds at row 8 until the internet answers.
  4. Case 2: the blob has the right size but zeroed blocks (allocated, never written) → the size-only check passes → iPXE is handed a broken kernel and the boot fails at the console.
A · recommended

Fsync Each Blob Before It Is Tagged

In store.PushBlob and store.TagArtifact

  • Layers: open the blob, Sync(), fsync blobs/sha256/
  • Manifest and config: written durably (ingest, fsync, rename, directory fsync) before oci.Tag indexes them
  • Only then can a tag name it, and the tag is already fsynced
Anything tagged survives a power cut. Neither case can happen. Utilities gain it too.
4blob fsyncs per Talos tuple (kernel, initramfs, cmdline, manifest), against ~100 MB downloaded
  • Keeps the core promise: once caches are warm, no install step needs the internet
  • Small and local to one function in internal/store
  • Reverses M2's accepted risk (in the safe direction), so M2's note is corrected

Re-Hash Talos Blobs At Startup

In Talos reconciliation

  • Read every tagged Talos blob and compare its sha256 to the digest
Case 2 becomes case 1: detected and refetched, not prevented.
~100MB read per tuple at every start
  • Also catches bit rot, not only power cuts
  • Still needs the internet to recover
  • Startup time grows with every tuple and, in M3b, every installer image

Where this bites: ZFS (TrueNAS, the day-to-day host) commits transaction groups in order, so a renamed blob never lands without its data; both cases are effectively absent there. They come from filesystems with delayed allocation, such as ext4 or XFS, which is what a recovery host on "any Linux host" (core goal 7) is likely to run.
